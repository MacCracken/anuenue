**Scope**: full source sweep. Run against the v1.3.2 tree, fixes shipped in
v1.3.3.

## Method, and why this sweep found something the last three did not

The previous audits worked inward from the **input** side: adversarial byte
streams, malformed UTF-8, chunk-boundary carry, argv at i64 extremes, signal
handling, terminal detection. That surface is now well covered — this sweep
re-ran all of it and found nothing new.

So the question that opened this sweep was: *what has no audit ever looked at?*
The answer was the **output** side. Three audits had asked "what if the input is
hostile" and none had asked "what if the write fails".

That framing found E-01 in the first ten minutes. It is worth writing down as
method: **an audit that keeps re-examining the same surface converges on
nothing.** Pick the surface by asking what has never been examined, not by
re-running what worked last time.

## Findings

### E-01 — every stdout write was unchecked; failures lost the stream and reported success · HIGH

`lib/io.cyr`'s `file_write` is a bare `sys_write`:

```
fn file_write(fd, buf, len): i64 {
    return sys_write(fd, buf, len);
}
```

It does not loop on a partial write. anuenue called it at **17 sites** and
discarded the return at every one, plus two raw `syscall(1, 1, ...)` writes.

Two independent, measured consequences — both of which **exited 0**:

| Scenario | Output lost | Exit code | What `cat` does |
|---|---:|---:|---|
| `anuenue < in > /dev/full` (ENOSPC) | **100%** | **0** | exits 1, prints the error |
| `anuenue < in > <non-blocking pipe>`, slow reader | **99.3%** | **0** | writes everything |

The second is the sharper one. It is not a contrived condition: any consumer
that sets `O_NONBLOCK` on the pipe it hands anuenue gets a partial write on the
first flush that fills the pipe buffer, and anuenue drops the remainder of that
flush and moves on. Measured: 1 000 000 bytes in, **7 290 out**, exit 0.

**Why HIGH.** anuenue's entire contract is byte preservation — it colours a
stream without altering it. Losing the stream while reporting success is the
worst available failure mode for that contract, and it is *silent*: no message
on any descriptor, and an exit code that tells a script everything went fine.
The trigger conditions are ordinary (a full filesystem, a quota, a non-blocking
consumer) rather than adversarial. And anuenue is the AGNOS-side `lolcat`, a
drop-in for a tool that gets this right.

**Present since M1.** The bare `file_write` call has been the shape of every
write since v0.2.0. Three audits missed it because all three worked the input
side.

**Fix** — `anuenue_write_all(buf, len)` in `src/observe.cyr`: loops until every
byte is written, returns `-1` on failure. All 17 call sites plus both raw
syscalls route through it and return `anuenue_write_failed()` on error, which
is an `agnostik` `STIK_ERR_IO` → exit 1 with `anuenue: i/o error: write to
stdout failed`.

Retry policy, because a naive loop would be wrong in two ways:

- **EINTR (-4)** — a signal interrupted the write before any byte moved. Retry
  immediately.
- **EAGAIN (-11)** — stdout is `O_NONBLOCK` and the consumer has not drained it.
  anuenue does not own that flag; a caller set it. The correct response to
  backpressure is to wait, exactly as a blocking write would, so it sleeps 1 ms
  and retries. **No attempt cap, deliberately**: a consumer that is alive but
  slow deserves backpressure, and a consumer that is *gone* yields EPIPE, not
  EAGAIN, which exits.
- Everything else, including a zero-byte return for a non-zero length, is fatal.

It lives in `observe.cyr` because `src/color.cyr`'s passthrough needs it and
`color.cyr` is included before `filter.cyr` — `observe.cyr` is the only module
every other one can reach ([architecture 004](../architecture/004-module-include-order.md)).
It also sits naturally beside `_eprint` and `anuenue_fail`: that file owns the
I/O that can fail and must be reported.

**One behaviour deliberately preserved.** `anuenue | head -1` must remain a
plain SIGPIPE (exit 141, nothing on stderr), not a confusing error. SIGPIPE's
default disposition kills the process before `write` returns, so the new error
path is never reached — verified, and asserted in `robustness-check.sh` so a
future change to signal handling cannot silently turn a normal truncated
pipeline into an error.

> ⚠ **CORRECTED at v1.3.4 (E-03). The paragraph above was wrong, and so was the
> assertion behind it.**
>
> SIGPIPE's disposition is *inherited*. The claim holds only where SIGPIPE is
> default — and there the branch under test never executes at all, so
> "verified" meant nothing. Where a parent has set SIGPIPE to `SIG_IGN` (a CI
> runner does, and children inherit it) `write(2)` returns `-EPIPE`, this fix
> classed that as fatal, and a routine `anuenue | head -1` printed an error and
> exited 1. **CI failed on the v1.3.3 tag for exactly this.**
>
> The `robustness-check.sh` assertion cited above did not catch it for two
> independent reasons: it ran only the default disposition, and it used a
> 256-byte corpus that fits inside a pipe buffer, making "is there a second
> write at all" a race. Both are fixed at v1.3.4, which runs the gate under
> both dispositions.
>
> Recorded here rather than silently edited: an audit that claims a case is
> verified, on evidence that could not have distinguished pass from fail, is
> exactly the failure mode this report's own method note warns about.

**Regression**: `scripts/robustness-check.sh` gate 5 — every colour mode, the
animation path and the positional-text path each write to `/dev/full` and must
exit 1 with the message; plus the EPIPE case above.

### E-02 — the escape-table cache was keyed on "built", not on which mode built it · INFO

`src/filter.cyr`. The 1 530-entry phase→escape table is built lazily and its
contents are **mode-specific** — truecolor, 256 and 16 produce different bytes
for the same phase. The cache guard was:

```
if (_PHASE_ESC_TABLE != 0) { return 0; }
```

So a second call after `ANUENUE_COLOR_MODE` changed returned the stale table,
and every subsequent character rendered in the *previous* mode with nothing to
indicate it.

**Not reachable in the shipped binary**: `main.cyr` resolves the colour mode
before dispatching and nothing changes it afterwards. It is a trap for the next
caller rather than a live bug.

It is recorded as a finding rather than a note because **it caught this audit's
own probe.** Measuring the per-mode escape lengths required zeroing
`_PHASE_ESC_TABLE` by hand between modes — the first run reported identical
lengths for all three. A cache that requires callers to know its internals is
the wrong shape, and the next caller will not have an audit watching.

**Fix** — key the cache on the mode. Same mode stays idempotent (the hot-path
property the M5 perf pass depends on); a changed mode rebuilds in place without
reallocating.

**Regression**: unit group "v1.3.3 E-02" asserts the three modes yield different
escape lengths *without* manual resets, and that re-init in the same mode does
not reallocate.

### Documentation — architecture note 001 asserted a byte count it had not measured

The note claimed "the longest escape actually emitted is truecolor:
`\e[38;2;255;255;255m` = 19 bytes". That is the worst case for the *format*, not
for anuenue: `hsv_rainbow` runs the cube edges at S=V=1, so one channel is
always 0 and the widest real form is `\e[38;2;255;254;0m` = **17 bytes**.

Measured maxima across the full table: 16-colour **5**, 256 **11**, truecolor
**17** — seven bytes of slack against the 24-byte payload budget. The bound held
either way, but a note in `docs/architecture/` whose numbers are *derived* rather
than *observed* is the kind that directory exists to replace. Corrected with the
measurement and the reason, and now pinned by the new unit group.

## Performance

The E-01 fix touches the hot path — 17 write sites gained a comparison and a
function call.

**Measured back-to-back in one session**, pre-fix binary rebuilt from the v1.3.2
tree, `RUNS=11` each:

| Corpus | Pre-fix (v1.3.2) | Post-fix (v1.3.3) | Δ |
|---|---:|---:|---:|
| ascii (no LF) | 46.47 ns/byte | 46.46 ns/byte | −0.0% |
| ascii (w/ LFs) | 50.54 ns/byte | 50.91 ns/byte | +0.7% |
| utf8 mixed | 41.52 ns/byte | 41.82 ns/byte | +0.7% |

A repeated single-corpus pass, to separate the cost from host drift:

| Pass | Pre-fix | Post-fix | Δ |
|---|---:|---:|---:|
| 1 | 46.74 | 46.80 | +0.1% |
| 2 | 46.63 | 46.91 | +0.6% |

So the honest figure is **a real but small cost, on the order of +0.5%** —
consistently positive across passes rather than lost in noise. That is what a
per-flush comparison should cost: the wrapper runs once per line or per 32 KB,
not per byte, so the added call is dwarfed by the `write(2)` it guards, but it
is not free.

Well inside the 60 ns/byte M5 acceptance, and the trade is not close — half a
percent of throughput against a defect that silently discarded 99.3% of the
stream and exited 0.

> **Method note.** An earlier draft of this section reported −0.5%, taken from a
> pre-fix baseline measured at the start of the sweep and a post-fix run taken
> half an hour later. Those two numbers were not comparable: host load drifted
> between them, and a third run of the same binary read 47.13 ns/byte. Only the
> back-to-back pairing above is a measurement of the change rather than of the
> machine. Same discipline the v1.2.2 and v1.3.2 cuts adopted for their own
> comparisons, applied here after nearly getting it wrong.

All six golden fixtures byte-identical. Micro-benchmarks unchanged:
`hsv_rainbow` 8 ns, `tty_fg_rgb_buf` 51 ns. Binary 814 448 → **814 480 B**
(+32).
