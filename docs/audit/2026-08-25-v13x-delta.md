## Finding

### D-01 — `_frame_wait`'s termination depends on a constant no code checks · INFO

`src/animate.cyr`. The slicing loop's only exit condition is `remaining`
decreasing:

```
while (remaining > 0) {
    var slice = remaining;
    if (slice > ANUENUE_TICK_MS) { slice = ANUENUE_TICK_MS; }
    sleep_ms(slice);
    remaining = remaining - slice;
    ...
}
```

If `ANUENUE_TICK_MS` were ever `0`, `slice` clamps to `0`, `remaining` never
decreases, and the loop spins forever — **inside animation, with the exit
signals blocked**. That is a SIGKILL-only hang, the same failure class B-02 fixed
from the other direction.

It is not reachable today: `ANUENUE_TICK_MS` is a module constant, no flag
touches it, and a unit test pins it positive. So the invariant is held by a
*test*, not by the code — and the test would still pass if someone later made
the tick configurable the way `ANUENUE_FRAME_MS` was made configurable at
v1.3.0. That is exactly the history this codebase has: `ANUENUE_FRAME_MS` sat as
a fixed constant from M4 until an `-i` flag reached it, and reaching it is what
exposed three defects.

**Fix** — a structural guard, `if (slice <= 0) { slice = 1; }`.

⚠ **Recorded as unproven**, in the cmdit 1.2.4 style: there is no failing test
behind this line. No public API call can drive `ANUENUE_TICK_MS` to zero, so
deleting the guard keeps the whole suite green. It is one comparison on a path
that is about to sleep, insuring against a failure mode that needs SIGKILL to
clear. The comment in the source says so rather than implying coverage it does
not have.

## Performance — the undischarged v1.3.0 gate

Head-to-head on one idle host, `RUNS=11`, rebuilt v1.2.2 binary vs the v1.3.2
binary.

**Filter path** — untouched by the arc, and the measurement says so:

| Corpus | v1.2.2 | v1.3.2 | Δ |
|---|---:|---:|---:|
| ascii (no LF) | 46.22 ns/byte | 46.61 ns/byte | +0.8% |
| ascii (w/ LFs) | 50.58 ns/byte | 50.88 ns/byte | +0.6% |
| utf8 mixed | 41.37 ns/byte | 41.41 ns/byte | +0.1% |

**Animation path** — the one the arc restructured. Mean CPU over three 3-second
runs at the default interval:

| | user | sys | total |
|---|---:|---:|---:|
| v1.2.2 | 2.3 ms | 2.7 ms | 5.0 ms |
| v1.3.2 | 2.7 ms | 2.3 ms | **5.1 ms** |

Within noise, as the default-path equivalence above predicts.

**Does slicing cost more at a long interval?** A 200 ms interval slices into ~13
ticks per frame instead of 1, so each frame pays 12 extra signal probes and 12
extra clock reads. Measured over 2-second runs:

| | user | sys | total |
|---|---:|---:|---:|
| `-i 16` | 1.1 ms | 2.8 ms | 3.8 ms |
| `-i 200` | 0.4 ms | 2.6 ms | **3.0 ms** |
| `-i 1000` | 1.3 ms | 1.8 ms | 3.2 ms |

Total CPU *falls* as the interval grows: the per-slice overhead is dwarfed by
the render work it replaces, because a longer interval means far fewer frames.
Slicing is free in practice, and responsiveness is not traded for anything.

Micro-benchmarks: `hsv_rainbow` 9 ns, `tty_fg_rgb_buf` 50 ns — unchanged within
the harness's own resolution.
